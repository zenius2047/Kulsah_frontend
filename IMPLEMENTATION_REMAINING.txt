Purpose
-------
This is the execution plan for completing the app. It records:

- What is already connected.
- What is still incomplete or powered by prototype data.
- How each remaining feature should be implemented in the frontend.
- The request payloads and response shapes the backend must support.
- Loading, error, cache, realtime, security, and test requirements.
- The decisions that must be confirmed before implementation begins.

Contract labels used below:

- EXISTING: The endpoint/type is already represented in the frontend source.
- EXTEND: An existing resource needs another method or response field.
- PROPOSED: The frontend does not currently have a confirmed backend contract.
  Backend and frontend must agree on it before implementation.

Do not silently implement a PROPOSED contract as if it already exists. First
confirm the path, authorization policy, payload, response, validation rules,
and realtime event names with the backend team.

GLOBAL API RULES REQUIRED BEFORE ADDING MORE ENDPOINTS
------------------------------------------------------

Base URL and environments
~~~~~~~~~~~~~~~~~~~~~~~~~

Current problem:

- `src/api/endpoints.ts` falls back to a temporary ngrok URL.

Required implementation:

1. Remove the ngrok fallback before production.
2. Keep one normalized API root ending in `/api/v1/`.
3. Configure the URL through EAS build profiles or environment files.
4. Fail startup in staging/production when the URL is missing; do not fall back
   to development infrastructure.

Required variables:

  EXPO_PUBLIC_APP_ENV=development|staging|production
  EXPO_PUBLIC_API_BASE_URL=https://api.example.com/api/v1/
  EXPO_PUBLIC_PUSH_TOKEN_ENDPOINT=general/device-tokens   # optional override

Recommended non-public server variables:

  GEMINI_API_KEY
  FCM_SERVICE_ACCOUNT_JSON or provider-specific FCM credentials
  APNS credentials
  payment-provider secrets
  livestream-provider secrets

Never put AI, payment, FCM service-account, livestream ingest, or signing
secrets in an `EXPO_PUBLIC_*` variable. Everything with that prefix is bundled
into the client application.

Request conventions
~~~~~~~~~~~~~~~~~~~

- Authorization: `Authorization: Bearer <access_token>`.
- JSON field names: snake_case.
- Dates: ISO-8601 UTC strings, for example `2026-09-01T18:00:00.000Z`.
- Money: decimal strings plus a currency code, never floating-point arithmetic
  for final accounting.
- KulCoin: integer coin values.
- Client-generated IDs: UUID v4 strings.
- Mutating financial, voting, order, gift, message, reward, and settlement
  requests must accept an `idempotency_key`.
- Upload endpoints must return the durable media/video ID before the media is
  attached to another resource.

Standard success envelopes
~~~~~~~~~~~~~~~~~~~~~~~~~~

Single resource:

  {
    "data": { "id": 123 },
    "message": "Optional human-readable message"
  }

Collection:

  {
    "data": [],
    "meta": {
      "current_page": 1,
      "last_page": 4,
      "per_page": 20,
      "total": 64
    },
    "links": {
      "next": "https://.../page=2",
      "prev": null
    }
  }

Standard error envelope
~~~~~~~~~~~~~~~~~~~~~~~

  {
    "message": "The given data was invalid.",
    "code": "VALIDATION_FAILED",
    "request_id": "req_01...",
    "errors": {
      "submission_ends_at": ["Must be after submission_starts_at."]
    }
  }

Frontend handling:

- 400: show a request-level message.
- 401: attempt one token refresh, then sign out if refresh fails.
- 403: show an authorization/eligibility message; do not retry.
- 404: show a deleted/unavailable state.
- 409: show conflict state and refetch the resource.
- 422: map `errors` to form fields.
- 429: respect `Retry-After` and disable repeated submission.
- 500+: retain user input and show retry.

1.2 Authentication refresh and 401 recovery
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Current problem:

- `AuthContext.refresh()` is a no-op.
- The auth store persists one bearer token in AsyncStorage.
- The Axios client has no response interceptor or request replay queue.

PROPOSED backend contract:

  POST auth/refresh

Payload when using rotating refresh tokens:

  {
    "refresh_token": "refresh-token-from-secure-storage",
    "device_id": "persistent-device-uuid"
  }

Response:

  {
    "data": {
      "access_token": "new-short-lived-token",
      "refresh_token": "rotated-refresh-token",
      "token_type": "Bearer",
      "expires_in": 3600,
      "user": { "id": 12, "role": "creator" }
    }
  }

If the backend uses secure httpOnly refresh cookies, confirm cookie support in
the native client and omit `refresh_token` from the JSON body.

Frontend implementation:

1. Add access token, refresh token, access expiry, and device ID to the session
   model.
2. Add `expo-secure-store` (or the approved native equivalent) and store refresh
   credentials there, not in AsyncStorage.
3. Add a single-flight refresh promise in `src/api/client.ts`.
4. On the first 401, refresh once and replay queued requests.
5. Mark replayed requests so a second 401 signs the user out instead of looping.
6. Exclude login, registration, OTP, and refresh calls from interception.
7. On logout, revoke the refresh token and push token, clear React Query, clear
   persisted auth, and reset navigation.

Optional revoke payload:

  POST auth/logout
  {
    "refresh_token": "current-refresh-token",
    "device_id": "persistent-device-uuid"
  }

Definition of done:

- Ten simultaneous 401 responses trigger one refresh call.
- Requests are replayed once with the new token.
- Refresh failure returns the app to Login without a request loop.
- Session restoration and logout are covered by tests.

10. CONSISTENT FRONTEND IMPLEMENTATION PATTERN
----------------------------------------------

For every new backend resource:

1. Add endpoint builders to `src/api/endpoints.ts`.
2. Add request/resource/response types under `src/types`.
3. Add an API module that returns the raw Axios response with typed data.
4. Add React Query keys and query/mutation hooks.
5. Normalize inconsistent legacy responses at the API boundary, not in screens.
6. Add screen loading, empty, error, retry, and pull-to-refresh states.
7. Add optimistic updates only when rollback is deterministic.
8. Invalidate the smallest relevant query set after mutations.
9. Add unit tests for payload builders/normalizers and integration tests for
   the screen flow.
10. Remove the replaced static source in the same change.

State ownership:

- React Query: server resources, pagination, network status, mutation state.
- Zustand: authentication session, small cross-screen client state, unread
  counters, active upload coordination.
- Component state: temporary form and modal state.
- AsyncStorage: non-sensitive preferences and recoverable unsynced drafts only.
- Secure storage: refresh tokens and sensitive device credentials.

List requirements:

- Use stable backend IDs as keys.
- Use FlatList virtualization for long/native lists.
- Do not mount every video player, query, or carousel in one list header.
- Play only the visible video and stop progress timers for inactive players.
- Use cursor pagination for messages and numbered/cursor pagination consistently
  for other resources.

Form requirements:

- Mirror backend validation rules in the UI without treating client validation
  as security.
- Preserve input after server failure.
- Map 422 errors to fields.
- Disable duplicate submissions while pending.
- Use an idempotency key for retryable mutations with side effects.

Upload requirements:

- Validate MIME type, duration, dimensions, and maximum size before upload.
- Initialize upload, upload directly to signed storage, finalize, then poll or
  subscribe to processing status.
- Support cancellation and retry without generating duplicate resources.
- Treat `ready` plus a returned playback URL as completion.
- Display backend processing errors and a retry-processing action.
